# v1.4.0 — Errors and API cleanup

Work plan for the `v1.4.0` entry in [ROADMAP.md](ROADMAP.md): a status-aware `AuthError` that tells a
rejected login code, a revoked session and a network failure apart (Lumen `v1.5.0` D1, bridge GAPS
§7.3 auth part), `GogDlError::SavesError` so the saves methods return `GogDlError`, and the removals
`v1.2.3`/`v1.3.2` scheduled here: `DownloadEvent::Preparing`/`Prepared`, `GameBuilds.game_title`, the
dead error variants, `SaveFile::relative_path`, and the `pub` items `a813975` left in private modules.
It ends the open question of `download_game` vs `repair_game` (D4).

`v1.4.0` is a **breaking** minor: every change in steps 2–9 is either a signature change or a removal.
It serves the bridge's `v1.5.0` (its breaking cleanup, ROADMAP "Lining up with consumers"), which
pins it and absorbs every break below Dart except the new login kinds, so Lumen migrates once, in its
`v1.5.0` Phase 7. Per Lumen's release order, `v1.4.0` is tagged and on the GitHub mirror before the
bridge starts its `v1.5.0`.

The plan covers `v1.4.0` and its three follow-up patches (`v1.4.1`–`v1.4.3`, under **Patches**), and
ends with writing `devlog/v1.4.0-errors-and-cleanup.md` and deleting this file (step 14).

## Merge requests

Every MR is opened from the push, with git push options, not from the web UI. The pipeline rules run
a branch only once it has an open MR (`$CI_COMMIT_BRANCH && $CI_OPEN_MERGE_REQUESTS`), so the push that
creates the MR is the one that starts its first pipeline.

```bash
git push -u origin <branch> \
  -o merge_request.create \
  -o merge_request.target=main \
  -o merge_request.remove_source_branch \
  -o merge_request.title='Step N: <theme>' \
  -o merge_request.description='<one line: what changes and why; gates pass locally>'
```

- Titles follow `main`'s history: `Step N: <theme>` for a step, `vX.Y.Z: <theme>` for a release (the
  `release` job and `CLAUDE.md` "Releasing" expect that), `Docs: …` for steps 0 and 14. The squash
  commit takes the title.
- Single quotes around the title and description: they hold backticks, which double quotes would
  run as a command substitution.
- A push option can't hold a newline, so the description is one line. The template's checklist
  (`.gitlab/merge_request_templates/Default.md`) is ticked in the web UI after the push, if step 0
  finds GitLab doesn't apply it to a pushed MR.
- Later pushes to the branch are plain `git push`; `merge_request.create` on an existing MR is a no-op.
- No `merge_request.merge_when_pipeline_succeeds`: each MR is reviewed and merged by hand once green.
- A tag push (steps 10–13) uses no push options.
