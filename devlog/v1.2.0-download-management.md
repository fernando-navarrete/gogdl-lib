# Devlog — v1.2.0 Download management

Everything the bridge's `v1.3.0` and Lumen's `v1.3.0` (D4–D7) asked of this crate, from the `v1.2.0`
ROADMAP entry, plus `v1.1.6` (cut early from the same branch) and the `v1.2.1`–`v1.2.3` follow-up
patches. Ran as nine phases and three patches; kept here for the decisions and pitfalls that aren't
obvious from the diff. `v1.2.0` is a **breaking** minor (free-space error fields, `#[non_exhaustive]`
on the event and error enums) and ships with the bridge change that adopts it. The line went into
`main` by fast-forward, so every tag's commit is in `main`'s history. `v1.2.1`–`v1.2.3` were tagged
after the fact, once the branch was finished.

## Phase 0 — Branch and baseline

Baseline on `1.98.1`: 72 unit, 9 integration and 12 doctests, all gates green.

**Decision:** cut `v1.1.6` from this branch rather than make Lumen wait for `v1.2.0`. Lumen marked
the free-space check (D4/D5) as blocking, while the bridge has a `statvfs` fallback and doesn't wait.
The additive half (`get_free_space`, the mount fix, the typo) is patch-legal; the error-shape change
waits for the minor.

## Phase 1 — Free space

**Pitfall (D5):** `sysinfo` lists mounts in `/proc/mounts` order and `/` comes first, so the old
"first mount that is a prefix" checked an install on `/media/gamedisk` against `/`. `pick_disk` takes
the **longest** match by path components (so `/media/game` doesn't match `/media/gamedisk`) and is
pure, so it's tested with a fake list in `/proc/mounts` order.

`PathResolver::new` runs `create_dir_all`, so it can't back a side-effect-free query. `get_free_space`
canonicalizes the nearest existing ancestor instead, since an install dir usually doesn't exist yet;
the pre-flight checks still go through `PathResolver` and share `pick_disk`. The mount fix is a
behavior change: the pre-flight check can now fail where it used to pass. `v1.1.6` was tagged only
after a local downstream run (lumen-cli built, the bridge's 41 tests passed).

Breaking half: `NotEnoughFreeSpace { required, available }` and `CouldNotResolveFreeSpace { path }` on
`DownloadError` and `ProtonError`, filled at the three call sites that used to say `Err(_)`.

## Phase 2 — Exports and event enums

**Decision:** `DownloadUnit` stays internal. No public signature exposes it, and exporting it would
also publish `FileType`, `_compressed_size` and two helpers. Only `FileSystemError`, `DepotFile` and
`Chunk` were exported. `FileMetadataError` and `FileCreationError` are never returned by a public
method (the engine turns those failures into stage events); they're documented as dead, not removed
(removal is `v1.4.0`).

**Decision:** mark the eight event enums, `FileSystemError`, `DownloadError`, `ProtonError` and
`SavesError` `#[non_exhaustive]` now, in the breaking minor, instead of doing `v1.2.3`'s event
changes here. Later patches can then add a variant (additive) without breaking a consumer's `match`.
Cost: outside code needs a wildcard arm, so `tests/public_types.rs` uses `_ =>` and the "a new
variant fails to compile" guard moved to an in-crate test that matches every variant.

## Phase 3 — One retry module

The eight hand-copied recovery sites now use one helper in `src/client/retry.rs` (not `src/retry.rs`
as planned), next to the HTTP client, its lowest-level user. It owns `MAX_ATTEMPTS`,
`MAX_HASH_ATTEMPTS` and `backoff`; the MD5 arm reads `attempt + 1 < MAX_HASH_ATTEMPTS`. The
unreachable `ClientError::AuthError` arm is gone.

**Behavior change:** `IncorrectGameId` and `ProductNotOwned` from `get_secure_links` return at once
(one lookup, not six), so downloading an unowned product fails in milliseconds instead of ~8s per
chunk. `v1.1.0`'s characterization test was flipped, every other `download_files` test passed
unchanged, and `bad_md5_is_only_retried_on_the_first_two_attempts` still fails under the same
mutation.

## Phase 4 — Cancel-safe contract

Each of the six long-running methods has a `# Cancelling` section: dropping the future stops the
work, what state it leaves, and the detached `spawn_blocking` step that finishes (chunk MD5, tar
extraction, a save write). No job uses `tokio::spawn`; a comment in `engine.rs` says it must stay so.

`repair_after_a_dropped_download_completes_the_install` is the test the bridge's §7.2 relies on. To
test the upload drop, the uploader's URL base became a `storage_url` field (`CLOUD_STORAGE_URL` in
production), and the fixture gained `Reply::Stall` and falls back to a path without its query.

## Phase 5 — Saves without truncation

`download_file` writes `.<name>.gogdl-part` next to the destination, sets the mtime, `sync_all`s, then
renames over it, with a guard that removes the temp file on error. The upload scan ignores leftover
`.gogdl-part` files. **Behavior change:** that temp file is briefly visible in the save directory,
and the write finishes even if the future is dropped. A drop *during* the write can't happen by
design (one `spawn_blocking`: the old file or a complete new one, never a partial one), so it has no
test.

## Phase 6 — Proton staging

Extraction goes into `.gogdl-staging-<tag>-<random>` under `path`; the old `path/<tag>` is moved into
the staging directory (deleted with it) and put back if the final rename fails. That fixes the
re-download overlay whether or not the archive root matches the tag.

**Pitfall:** `Drop` can't await, and a blocking extraction that outlives its staging directory keeps
writing into a deleted tree. So the `StagingDir` guard is moved *into* the extraction task, which
removes the directory itself after it has stopped writing; the async side only drops it once
extraction returned. Stale staging directories from a crash are removed at the start of the next
download into the same `path`. **Behavior change:** the staging directory is visible during a
download, an empty sanitized tag now fails before the transfer, and an existing `path/<tag>` is
replaced wholesale. The free-space check stays on the compressed size, since the asset has no
extracted size.

## Phase 7 — Per-product sizes

**Decision:** `GogDl::get_product_sizes(game_id, build_name) -> Vec<ProductSize>`, summed per
`productId` over the build's (language-filtered) depots. `Depot` stays internal. One metadata fetch,
no manifests. Checked against a real build (`tests/fixtures/build_metadata_dlc.json`, base game plus
two DLCs): the metadata sums equal the manifest sums from `get_product_bundles` exactly, for both
`size` and `compressed_size`. The build lookup three callers shared became
`DownloadManager::get_build_metadata`.

## Phase 8 — Release `v1.2.0`

The downstream run went red as expected, only on nine non-exhaustive `match`es in each consumer, all
from `#[non_exhaustive]` (nothing used the free-space variants). Each was fixed with a `_ =>` arm on
an unpushed `scratch/gogdl-lib-v1.2.0` branch in the bridge (`feat/v1.3.0-downloads`) and `lumen-cli`
(`feature/remote-config`): lumen-cli built and passed 103 tests, the bridge 41. The CI `downstream`
job builds their `main` without those fixes, so it stays red until they adopt `v1.2.0`.

## P1 — `v1.2.1`: `repair` skips checksumming freshly allocated ranges

Only chunks past a file's *old* length skip the MD5: `set_len` keeps a resized file's existing
bytes, so those below it are still hashed. A missing file skips entirely. Skipped units still emit
their `VerificationEvent` (`ChecksumMismatch`, what the all-zero range produced before), so the event
count is unchanged. **Accepted:** a chunk of real all-zero content used to verify and is now
re-fetched.

## P2 — `v1.2.2`: `download` and `repair` share one pipeline

`Downloader::pipeline` takes which units to fetch (`All` or `Verified`), with a `staged` helper for
the channel/forward/join boilerplate. The stage-sequence tests were committed *before* the refactor
(`a0c9248`) and passed unchanged after it.

**Decision:** the refactor only. ROADMAP's "download skips chunks that already verify" would make
`download_game` a resume and add a `VerificationStage` to its events, a behavior change behind an
unchanged signature, so it isn't a patch. `repair_game` is already the resume path; GAPS keeps
"`download` re-downloads every chunk" open.

## P3 — `v1.2.3`: a compressed total for download progress

`DownloadEvent::Started { compressed_total }` is sent once after `Prepared`, summed from
`DownloadUnit.compressed_size` of the units being fetched (so for `repair`, only the missing ones).
`Progress` deltas net to it on success and `ProgressRegression` keeps it honest across retries
(`progress_nets_to_the_compressed_total_with_a_retried_chunk`). `Preparing`/`Prepared` are
`#[deprecated]` but still emitted; removal is on `v1.4.0`'s list. This is additive only because
Phase 2 made the enum `#[non_exhaustive]`.
