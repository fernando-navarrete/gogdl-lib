# Devlog — v1.3.0 Library and account

What the bridge's `v1.4.0` asked of this crate (`clear_cache`, `remove_products`), plus owned games
that don't silently shrink, `download_game` that resumes, cheaper library lookups, one "not a game"
answer and no mutex held across a network call. Ran as steps 0–16 of a work plan (deleted with this
devlog) and the patches `v1.3.1` and `v1.3.2`. Each step was one branch and one squash MR. `v1.3.0` is
a **breaking** minor (`OwnedGames.unresolved`, `VerificationStage` in `download_game`'s events,
`ProductNotAGame` from three more fetchers) and ships with the bridge change that adopts it. SHAs are
commits on `main`: `97ce2da` (secure-link dedup), `c346c43`, `a5f4cb4`, `b15c750`, `53c4e3d`,
`df16657`, `3ea0302`, `3c13670`, `c6d507c`, `e98237e`, `8331fcf`, then the releases `0b11306`
(`v1.3.0`), `33f927c` (`v1.3.1`) and `8df36d0` (`v1.3.2`).

## Decisions

- **D1, no `v1.2.4`/`v1.2.5`.** `clear_cache` and `remove_products` were to ship first as additive
  patches so the bridge could pin a `v1.2.x` with nothing breaking. Tags go on `main`, so once a
  breaking step merges, `main` can no longer cut a `v1.2.x`. Both methods became steps 4–5 of `v1.3.0`
  instead. Cost: the bridge's `v1.4.0` absorbs the breaking parts in one go.
- **D2:** `OwnedGames.unresolved: Vec<ProductId>` with `#[serde(default)]` and no `#[non_exhaustive]`,
  so old JSON still deserializes and a consumer can still build it with a literal. A `gamesdb` 404 is
  unresolved too; the caller decides. A `Vec<(ProductId, GamesError)>` would give the reason but isn't
  `Clone`/`Deserialize` without more work.
- **D4:** `download_game` runs the verified pipeline `repair_game` used. The two do the same now; both
  stay, and deprecating one is on `v1.4.0`'s list. `Units` went away.
- **D5:** `clear_cache` keeps what is keyed by an immutable id (a product's `gamesdb` type, a build's
  metadata) and drops what GOG can change or what is big (`RemoteConfig`, `DepotInfo`).
- **D6:** populate `GameDetails.id`; `GameBuilds.game_title` can't be had without a second request,
  so its removal moved to `v1.4.0`.

## No mutex across the network

The hosts are hardcoded, so a fixture server can't park `get_game_builds`. The three tests hold
`GamesManager.inner` themselves: a cold call parks at the await the outer lock used to span, and a
cached call completes under `start_paused` and a timeout. Each fails if the old lock is put back.
The fix is mechanical: the cheap `Clone` handles (`games`, `depot`, `secure_links`) moved out of the
`Inner` structs, which keep only caches.

## Secure-link dedup

A per-`game_id` `Arc<OnceCell<_>>` (the shape `PathResolver::dir_cache` uses) so N callers share one
ownership check and one fetch. **Pitfall:** `SecureLinksError` isn't `Clone`, so waiters can't share
the leader's error without a new public variant (breaking); queued waiters retry one at a time, each
with its own error, and a failure isn't cached. `invalidate_secure_links` takes the set the caller
used and evicts only if it is still the cached one, so a late 401 doesn't evict a sibling's fresh
fetch; the engine's fetch-error path no longer invalidates (nothing was cached).

## Caches and `clear_cache`

Only a successful `gamesdb` lookup is cached; step 11 depends on a failure being retried.
**Measured for step 7** (newest public build): Cyberpunk 2077 has 10 manifests, 5.6 MB of JSON, about
3 MB in memory; Baldur's Gate 3 has 13 manifests, 44.7 MB of JSON, 127,169 files and about 60 MB in
memory. Hence `clear_cache` drops `DepotInfo`, for memory. A fetch in flight during a clear may
repopulate its entry, but never leaves a half-built one. `OwnedProducts` used to re-fetch only while
the list was empty; it now re-fetches after a clear.

## `remove_products`

Alien: Isolation's DLCs share files with the base game, so it deletes only what `remove`'s depots
list and `keep`'s don't, compared case-insensitively on normalized paths. A path that would escape
`path` after normalization is never deleted, an already-missing file is success, an empty `remove`
fetches nothing, an id in both lists is kept. A failed delete is the new
`FileSystemError::FileRemovalError`. Cancel-safe like the downloads: a dropped call is finished by
calling it again.

## One "not a game" answer

Step 9 captured a DLC and a pack from a real account. Every endpoint answers **200**; none 404s.

| Fetcher | Non-game signal |
|---|---|
| `get_game_details` | body is `[]`, not an object (it was a decode error, and its `ProductNotAGame` was unreachable) |
| `get_game_builds` | `count: 0`, indistinguishable from a game with no build |
| `get_game_links` | `_embedded.productType` is `DLC`/`PACK` |
| `get_game_summary`, `get_owned_games` | `gamesdb` `type` is `dlc`/`spam` |

**Decision:** for an empty builds list, consult `gamesdb`'s type (cached, shared with
`get_owned_games`); a failed lookup caches nothing. The `"game"` comparison lives in one place. The
saves methods inherit the answer through `get_game_builds`.

## `download_game` resumes

`download` takes the verified path, so its events gain a `VerificationStage` and `download_stage_sequence`
changed in the same commit. A test over a half-finished install counts requests at the fixture server
and sees only the missing chunks fetched.

## Releasing `v1.3.0`: the downstream run

**Pitfall:** the `downstream` job patched only the GitLab URL, but the bridge pins the GitHub mirror
(since its `v1.3.3`), so its half had been testing `v1.2.3`. It patches both now. Run locally against
`v1.3.0`: the bridge's 65 tests passed unchanged (its translators already match `VerificationStage`,
and it builds no `OwnedGames` literal). `lumen-cli` (pinned `v1.0.10`) got 9 `E0004` non-exhaustive
matches in `src/middleware/{downloads,proton,saves}.rs`, all from `v1.2.0`'s `#[non_exhaustive]`
events, fixed with a `_ => {}` arm each (103 tests pass). Nothing there reads `OwnedGames`. Neither
change was committed from this plan; `lumen-cli`'s bump goes on `feature/remote-config`, its `main`
still pins `v1.0.4`.

The tag pipelines for `v1.3.0`–`v1.3.2` were the first real runs of the `release` job's on-`main`
rule, and all went green. `v1.3.2` is a lightweight tag, unlike `v1.3.0` and `v1.3.1`, which are annotated.

## Patches

- **`v1.3.1`:** `GameScreenshots::resolve_links` took `formatters.get(2)`. Every captured screenshot
  lists `product_card_screenshot_112`, `_748`, `_748_2x`, `1600`, so index 2 was `_748_2x`; it is now
  picked by that name. A link that doesn't list it uses its last formatter (GOG lists them smallest
  to largest) instead of being dropped; only one with no formatter at all is. Resolved URLs are
  unchanged for every product sampled.
- **`v1.3.2`:** `GameDetails.id` is set from the requested id before caching (it was always `0`).
  `GameBuilds.game_title` stays `""`: the builds listing carries no title. Its removal is in `v1.4.0`.
